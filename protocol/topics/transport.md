# 资源运输与行军油耗机制

> 本文档记录游戏中资源跨城调配的底层交互协议、数值模型与实测结论。
> 协议数据来自真实会话实测验证。

---

## 1. 核心业务与协议链路

游戏内城池资源储量到达容量上限后自然增长将停止，但通过外部调运可突破容量上限。资源调运依赖部队远征系统中的 **TRANSPORT（类型 2）** 指令。

```
[客户端]                                          [游戏服务端]
   │                                                   │
   │<── 登录成功后主动推送 cmd=26022 调度 key ──────────┤ (8B u64, 约每分钟刷新)
   │                                                   │
   ├── cmd=19009 (查询当前城驻军) ─────────────────────>│
   │<── 返回各兵种存量 (含卡车 armyId=3) ────────────────┤
   │                                                    │
   ├── cmd=2003 (查询当前城资源与容量) ─────────────────>│
   │<── 储量与容量 (food@4/8, steel@32/36...) ──────────┤
   │                                                    │
   ├── cmd=19003 (执行运输, 携带最新 26022 key) ────────>│
   │<── status=1, truce_tag=0 (资源即时扣减, 部队出征) ──┤
```

### 关键命令要点

1. **`cmd=26022` 调度功能 key（服务端主动推送）**：
   - 登录完成后服务端自动下发，载荷为 8 字节 `u64 key`。
   - 会话期间 key 会不定期刷新（实测约 1 分钟更新一次），每次更新重新推送。
   - **`cmd=19003` 的末尾字段必须传入当前会话最新收到的 key**，传入过期或未初始化的 key 服务端返回 `status=-1` 拒绝。

2. **`cmd=19009` 当前城驻军查询**：
   - 响应格式为 `u32 count + N × (u32 armyId + u32 count)`。
   - 客户端仅收录 `armyId ∈ [1,16] ∪ [30,34]`，卡车原型为 `armyId=3`。

3. **`cmd=19003` 执行运输（expeditionType = 2）**：
   - 非寻路模式（`mode=0`）明文参数固定为 93 字节（AES 加密后 96 字节）：
     ```
     u8  army_kind_count = 1
     u8  army_id = 3                          // 仅允许卡车
     u32 truck_count                          // 车辆数量
     u32 target_x, target_y                   // 目标城池坐标
     u8  expedition_type = 2                  // TRANSPORT
     u8  0
     i64 commander_id = -1                    // 运输不需要名将，填 -1
     u32 0
     u64 carry_food/steel/oil/mineral/gold    // 5×8B 资源携带量 (ResourceType 枚举顺序)
     u32 transport_time_interval = 0          // 手动模式填 0 (非内置自动运输)
     u32 transport_total_num = 0              // 手动模式填 0
     i32 assembly_id = -1                     // 客户端缺省 -1
     i32 alliance_capital_fort = -1           // 客户端缺省 -1
     u8  is_break_truce = 0
     u64 key                                  // 最新 26022 调度 key
     ```
   - 响应仅包含 1 字节 `truce_tag=0`（若遇停战确认则置 1 并附带提示文案）。

4. **`cmd=19015` 我的远征列表边界**：
   - 实测服务端对空参 19015 请求**静默丢弃**（无响应直接超时）。
   - 该接口在客户端仅用于地图大网格寻路（FIND_PATH）视图，常规自动化脚本不应依赖 19015，行军状态可通过地图行军线路（`cmd=15015`）或服务端警报列表（`cmd=19007`）间接获取。

## 2. 兵种属性与数值模型

基于兵种原型表（`cmd=3007`）与实测数据：

| 兵种 | armyId | 单车载重 | 单车油耗基数 | 基础移速 | 说明 |
|---|---:|---:|---:|---:|---|
| 卡车 (GMC/L300) | 3 | 1200 | 15 | 1150 | 唯一合法的运输载具 |
| 侦察机 (蚊式/Fi-156) | 9 | 5 | 20 | 5000 | 速度极快，用于侦察与警戒 |

### 行军时间计算

两城坐标为 $(x_1, y_1)$ 与 $(x_2, y_2)$，地图欧氏距离：
$$D = \sqrt{(x_1 - x_2)^2 + (y_1 - y_2)^2}$$

**两种口径必须区分**（实测交叉验证，勿混用）：

**① 油耗口径 T（基础速度，服务器按它扣油）**——取自客户端常量 `MARCH_MIN_TIME=30`, `MARCH_ONE_TILE_DISTANCE=100000`：
$$T_{\text{base}} = 30 + \frac{D \times 100000}{V_{\text{base}}}$$
其中卡车基础移速 $V_{\text{base}} = 1150$（3007 原型 moveSpeed），每格约 86.96 秒。

**② 真实行军时间（含加成，界面展示用）**——客户端发起远征前先请求 `cmd=19001` 取实时加成：
$$V_{\text{real}} = V_{\text{base}} \times (1 + \text{landSpeedAdd} + 0.5 \times \text{运输站等级}) \times \text{speedFactor}$$
$$T_{\text{real}} = 30 + \frac{D \times 100000}{V_{\text{real}}}$$

| 输入项 | 来源 | 实测样本 |
|---|---|---|
| `landSpeedAdd` | 19001 `land_spped_addition_percent`（%） | +50%（0.5） |
| `speedFactor` | 19001 `global_army_speed_add`（倍率） | 3 |
| 运输站等级 | 17001 出发城建筑（proto=20，等级 0~10） | 9 |

> **加成取出发城**（同距离反向对照实测确权：站 L10 出发 V≈22445、站 L9 出发 V≈20728，
> 各自与出发城等级吻合）。实测样本中 $V_{\text{real}} = 1150 \times 6.5 \times 3 = 22425$（L10）
> 或 $1150 \times 6 \times 3 = 20700$（L9），与反推值误差 <0.3%。运输站等级 0~10 使速度相差 4.3 倍。
>
> **验证方法**：发一笔 1 卡车微型运输后立即查 `cmd=19008` 的初始 `remain_time`，加上查询延迟即为 $T_{\text{real}}$。

### 实测油耗拟合公式

实测扣除石油量与**货物量无关**（运 10 资源与 50 资源油耗恒定），由**油耗口径** $T_{\text{base}}$ 与车辆数 $N$ 决定。经 296 格线路 2~8000 辆卡车的多尺度复核，总耗油对车辆数呈**线性**，单均约 19.7 油：

$$\text{Oil} \approx \text{round}\left(0.01313 \times T_{\text{base}}^{0.72} \times N\right)$$

> **关键实测**：油耗与实时速度加成**无关**——真实速度比基础快 ~18 倍时，扣油仍与 $T_{\text{base}}$ 的预测吻合
> （3 笔交叉验证：d=372 格实测扣 24 油 vs 预测 23.22；d=34 格实测 4 vs 预测 4.19）。
> 估算油耗必须用 $T_{\text{base}}$；用 $T_{\text{real}}$ 会低估约一个量级。
>
> **早期小样本（1~3 辆车）曾误拟合出 $N^{0.7}$ 亚线性指数**——那只在该量级附近成立；大车队下按 $N^{0.7}$ 估算会严重低估（本例低估约一个数量级），发车时因「城内资源不足」被服务器拒绝。已按线性口径修正，2~8000 辆车全量程偏差 <2%。
>
> **工程要点**：发车前必须以「单均油耗 × 车数 + 石油类货物量 ≤ 城内石油」校验预算（服务器在发车时校验并即时扣油），预算不足的任务会整单被拒。

## 4. 对自动化资源调配的结论

1. **油耗并非调度主要瓶颈**：即使跨越 250 格地图，单辆卡车往返油耗仅需 18 点石油。相较于单卡车 1200 点的高额载重量，调运油耗损耗率低于 1.5%。
2. **时间也不是主要瓶颈**（含加成后修正）：实测带加成速度为基础速度的 18 倍（$V_{\text{real}}=20700$，基础 1150），
   250 格单程仅约 20 分钟（旧口径按基础速度估算的「约 5 小时」已被实测推翻）。真实耗时以 `T_real` 公式为准。
3. **架构建议**：资源调配仍按「地缘邻近分群/小区域互助」组织——不是为省时间，而是缩短卡车占用周期、
   让运力更快周转；但不必因「太远」放弃跨区调运（全程分钟级）。
4. **真正的硬上限是「出征位」**（实测标定）：每城同时在外部队数 ≤ 该城司令部等级，超发被拒（提示升级司令部）。
   每笔运输（无论大小）占 1 个出征位，上限与
   车队规模无关 → **小批量多笔是最差策略**，必须「同路合并、多资源混装、凑大批量」，单笔可混装多种资源（实测通过）。

## 5. 出征位（并发远征上限）机制

| 项 | 结论 | 依据 |
|---|---|---|
| 上限值 | 每城独立 = 该城司令部（HEADQUARTERS, proto=13）等级 | 多城逐笔标定：HQ9 城「在外 3 笔 + 连发 6 笔成功」后第 7 笔被拒；HQ12 城「在外 5 笔 + 连发 7 笔成功」后第 8 笔被拒；HQ12 城满额全拒 |
| 全局性 | 无账号级全局上限 | 实测全局在外数 127 时仍有个别城可发 |
| 占用计数 | 与 `19008` 该城条目数一致（每笔远征 1 条，与携带资源量、车队规模无关） | 标定实验中 3 城「在外数 + 连发成功数」精确等于 HQ 等级 |
| 释放时机 | 部队返程到城后条目消失、位恢复；返程中的部队（19008 仍列出）占用计数仍有效 | 以 19008 实时列表为准 |
| 查询 | `cmd=19008`（分页 50/页，`page_num` 从 1 起）列出本账号全部在途部队，按出发城坐标 `start_x/start_y` 统计占用 | 实测 |
| 算法要求 | 规划发车前须先查 19008 统计各城占用，剩余位 = 上限 − 占用；超限的城跳过，等返程后下次运行 | 本次实现 |

> **实测边界**：标定样本全部为运输（`expedition_type=2`）。侦察/掠夺等其他远征类型是否同样受此上限约束、是否共享同一计数，未单独验证——
> 但从「出征在外的部队数」的语义与 19008 全类型统一列表的形态推断，同一城的各类远征大概率共享此配额。

> **发车被拒的识别特征**：服务器提示出征数超限、建议升级司令部——
> 与「城内资源不足」「目标不可达」等业务拒绝区分开，前者是配额问题（等返程/升级司令部），后者是资源问题。
