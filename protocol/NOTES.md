## 响应字段规律

- `10001` 响应条目：`u32 ID` + `u32 长度` + `UTF-8 名称` + 若干状态字段
- `26003` 推送末尾：任务 ID 以**十进制字符串**形式出现（如 "307" / "5042"）
- `10003` 响应：成功时含物品列表（重复块 `256, 1394, <物品标识>, 80000, 0`）；
  重复领取时返回 `ff000000 | u32 长度 | "已领取过该任务奖励"`
- `26044`：会话 ID（UUID）

## 平台说明
样本来自 iOS 端，但服务端为双端统一实现（配置下发里同时存在 android 相关路径），
故帧格式/命令字应与平台无关；Android 端若有差异，多半只在握手包里的渠道名、机型字段。

## 任务列表有「分类」概念（2026-09-08 探明）

`cmd=10001` 的请求参数（16B）决定返回哪个分类，不同参数返回完全不同的任务集：

| 参数(前8位) | 返回的任务 |
|---|---|
| `fea43ec4` | 231 司令 / 272 沿海要地 / 859 / 2159（军衔·称号类） |
| `14a76e22` | **290 职位工资 / 307 军衔补助 / 5042 钻石奖励** / 15138 / 50620（日常军事） |
| `f3b21e6e` | 15470 / 50620（日常类） |

→ 所以「可领列表查不到 307/5042」不是重置问题，是**分类不对**。
  若要查全，需对每个分类参数各查一次。

**注意坑**：解析 ID-名称对时，过滤下限不能设太高（曾设 500，导致 307/290 全部漏掉）。

**290 职位工资**的领取帧仍未拿到——领取参数（16B）是客户端生成的（疑似加密/随机），
两个样本（307、5042）推不出规律，只能靠抓一次点击获取。
