## 1. 每日任务

三条全部可自动领取，帧存于 `protocol/frames.local.json` 的 `claims`：

| ID | 名称 | 奖励 |
|---|---|---|
| 290 | 职位工资 | 黄金 |
| 307 | 军衔补助 | 资源（粮食 / 钢铁 / 石油） |
| 5042 | 钻石奖励 | 10 钻 |

- 属于**每日任务**性质：点一下即完成，每天刷新，可重复领取。
- ID 每天不变，因此领取帧可长期使用。

## 2. 服务器每日重置时间

**≈ 00:00**（实测：23:45 领取返回"已领取过"，次日 00:24 领取成功）。

注意：重置后可能有短暂延迟，建议定时任务设在 00:10 之后。

## 2.5 会话与多端互斥（重要）

**同一账号在业务长连接上只能维持一个会话。** 新会话建立后，旧会话会被服务端断开——
表现为客户端弹出"断开连接 / 请关闭客户端"。

实测现象：
- 脚本 `hello → login` 之后，正在运行的客户端立刻被挤下线。
- 反过来也一样：在客户端重新登录，脚本的连接会失效。

**对自动化的影响：**

- 定时任务应安排在不玩游戏的时间段（如凌晨），避免互相打断。
- 一次运行内**只建立一个连接**、顺序完成所有操作（`w2signin.js` 已按此设计：
  登录一次 → 依次领取所有已收录任务，而不是每个任务重连一次）。
- 若脚本中途另建连接，会把自己的前一个连接挤掉，导致后续操作失败。

## 3. 任务列表有「分类」概念（重要）

`cmd=10001` 的请求参数（16B）**决定返回哪个分类**，不同参数返回完全不同的任务集。
已知 5 个分类（值为参数前 8 位，完整值见 `frames.local.json`）：

| 参数前缀 | 内容 |
|---|---|
| `14a76e22` | **日常军事**：290 职位工资 / 307 军衔补助 / 5042 钻石奖励 / 15138 / 50620 |
| `fea43ec4` | 军衔·称号：231 司令 / 272 沿海要地 / 859 / 2159 |
| `f3b21e6e` | 日常：15470 / 50620 |
| `7e82cd02` | 兑换：3448 兑换-绿色奖章 / 3764 迁城行动 / 50628 |
| `3ba2d423` | 名将兑换：11179 / 11200 / 11243 |

**踩过的坑**：单一分类查不全，曾因只查 `f3b21e6e` 而误判"任务未刷新"。
因此 `w2signin.js` 已改为**不依赖列表、直接尝试领取**（重复领取会被服务器拒绝，无副作用）。

## 4. 编码

- 字符串：**UTF-8**，无 BOM。长度前缀是**字节数**不是字符数（中文 3 字节/字）。
  - 例：「钻石奖励」4 字 → 长度 12；「已领取过该任务奖励」9 字 → 长度 27。
- 邮件/公告正文是富文本，内嵌 HTML（`<br />`、`<font color=#FF0000>`），换行 `\r\n`。

## 5. 响应字段规律

- 通用编码：4 字节大端长度前缀字符串 与 裸 u32 整数混编（非自描述，按命令解析）。
- `10001` 条目：`u32 ID` + `u32 长度` + `UTF-8 名称` + 若干状态字段。
  - 解析注意：ID 过滤下限别设太高（曾设 500，导致 290/307 全部漏掉）。
- `26003` 推送：末尾带**十进制字符串 ID**，两种用途——
  - 任务领取提示（如 "307" / "5042"）；
  - 活动上线/更新通知（如 "85" / "10197" / "22515" / "22847" / "8268" / "2838" /
    "4227" / "3231" / "50202" / "999999"），ID 后随字面量 "活动名称"，触发客户端
    拉取 `22002` 配置同步（一个活动一条 26003+22002 成对出现）。
- `6016`：稳态（fieldA=0xffffffff）**周期查询**，约 1 次/秒。载荷 36B =
  命令(4B) + 16B 变化段 + 16B 固定尾（`ada58444 6ba69021 643dcf85 f4ef969d`，
  3 次采样不变）。响应不定长：33B / 42B / 6132B（大表）。16B 固定尾与领取帧
  「末 16B 校验」不同——领取帧校验随任务变化且夹在 16B 参数内，此处固定尾更像
  固定查询键；两处机制是否同源待进一步对比。
- `10003` 响应：
  - 成功 → 较长，含物品列表（重复块 `256, 1394, <物品>, 80000, 0`）
  - 重复领取 → 短（`len≈36`），提示"已领取过该任务奖励"
  - 参数不合法 → **无任何响应**（静默丢弃）
- `26044`：会话 ID（UUID）；`26001`：会话建立通知。

## 6. 领取参数（payload 末 16B）的本质

对照实验（样本 290 / 307 / 5042）：

| 改动 | 结果 |
|---|---|
| 原样重放 | ✅ 正常响应 |
| 参数改全 0 / 随机 | ❌ 静默忽略 |
| 换用别的任务的参数 | ❌ 静默忽略 |
| 只改序号 +1 | ❌ 静默忽略 |
| 只改 nonce 一字节 | ❌ 静默忽略 |
| 只改 fieldA | ❌ 静默忽略 |

→ **它是对整帧的校验/签名值**，与序号、nonce、fieldA 全部相关。

已排除：`md5(十进制ID)`、`md5(u32BE/LE)`、`sha1`、`sha256`、`md5(帧头37B)`、`md5(nonce)`、`md5(nonce+cmd)`。
推断为 **HMAC 或带会话密钥的对称加密**（TEA / AES 类）。

**实践影响：**
- ✅ 整帧原样重放长期有效（跨天验证通过），服务器**不防重放**，同一帧可反复发送。
- ⚠️ 无法凭空构造新帧；每个新操作（如造兵）需抓一次包取帧，之后永久重放。
- 彻底破解需逆向客户端（砸壳 IPA → 定位加密函数），对重放式自动化非必需。
